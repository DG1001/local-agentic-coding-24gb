Field notes — Apple M5 Pro, 24 GB

Local agentic coding on a 24 GB Mac: the system prompt is the benchmark

Six models, 202 tool calls, six identical runs per configuration. Every model aced the task in isolation. What separated them was a five-thousand-token system prompt — the thing every real coding agent sends. All three then repaired a genuinely broken module — 6/6, 3/4 and 2/2, at 55, 177 and 132 seconds. Along the way: one kernel panic, a flickering desktop as the only warning macOS ever gave, and eleven confident conclusions I had to retract.

The task was identical throughout: write greet.py with a greet(name) function, run it with python3, verify the output, fix it if wrong. Two tools available, bash and write. Six runs per configuration, success measured by actually importing the resulting file and calling the function.

Finding 1It holds up on real work

Everything above uses a deliberately tiny task, which proves less than it looks like. So the last test was a small but genuine repair job: an existing 100-line ISO-8601 duration module with a 22-test suite, seven of them failing, from three independent bugs in different places — a missing feature (week designators absent from both the regex and the unit table), a crash (int() on fractional values), and a logic error (the sign captured but never applied). Instruction: make the suite pass, do not touch the tests.

gpt-oss wins on all three axes at once: more reliable, three times faster, and with 17 percentage points more memory headroom. The Qwen MoE is the slowest despite activating only 3B of its 35B parameters — its failures are expensive, and its one bad run burned 8,211 reasoning tokens going nowhere.

Devstral is credible on quality — it never failed and never touched the tests — but llama.cpp on Apple Silicon costs roughly 2.4× the wall time of MLX, because it does not use the M5's neural accelerators.

Turning off reasoning does not help

An obvious idea, since Devstral solves this task with reasoning_tokens: 0: disable thinking on the Qwen MoE and skip the loop entirely. Measured on the same request:

ModeReasoning tokCompletion tokTimeTool call

Without thinking the model stops calling tools altogether and rambles to the token limit. For Qwen3.6 the reasoning is load-bearing for tool use — you cannot strip it and get a non-reasoning model's behaviour. Devstral works without it because it was trained that way, not because thinking is optional. (Note that chat_template_kwargs: {"enable_thinking": false} is silently ignored by LM Studio; only the /no_think token in the message actually takes effect.)

The patch reads like something a person would write: the week group inserted at the correct grammatical position (before the T separator, where ISO-8601 puts it), int() changed to float() and the accumulator initialised to 0.0 — the second half being the part that is easy to miss — and four lines applying the sign after summation. No invented features, no gratuitous restructuring.

Note the variance: run 5 finished in 4 tool calls and 556 reasoning tokens, run 4 needed 2,605. A factor of 4.7 on an identical task. Single runs tell you very little here.

Finding 2One malformed tool call in 202

The question that started this investigation was whether 3-bit quantisation was corrupting tool arguments. Across the whole study — six models, three prompt sizes, two sampling regimes, plus the repair task — 202 tool calls produced exactly one schema failure: a write with a completely empty arguments object. The agent recovered on the next step and the run still went green.

The harness validated this itself rather than trusting the agent framework, declaring the JSON schema and checking every incoming call against its own required list before executing it.

One detail is suggestive but unproven: the single failure came on the real task, where write arguments carry an entire 1,400-token source file, not the two short strings the toy task needed. Large arguments may well be where this risk lives. One occurrence is not evidence, and I am flagging it as a hypothesis rather than a finding.

The distinction that matters

"Model emits broken tool arguments" and "model does not emit tool calls at all" look identical in an agent's error log and have nothing in common underneath. The first would point at the quantisation. The second — the one that actually happened — points at instruction following under context pressure. I spent hours on the wrong one.

Finding 3Sampling parameters rescue a fragile model and are irrelevant to a robust one

Qwen's documented recommendation for thinking mode is temperature 0.6, top_p 0.95, top_k 20. I had been running temperature 0.3 with no truncation parameters at all. On the Qwen MoE the difference is not subtle:

Qwen3.6-35B-A3B, same prompt, same model, same minute
SamplingReasoning tokensWall timeFinish reasonResult
temp 0.3, no top_k / top_p 8,191143 slength nothing
temp 0.6, top_p 0.95, top_k 20 1054 stool_calls correct call

A 78× difference in reasoning tokens from four numbers. Low temperature without nucleus and top-k truncation drives this model into a repetition loop. The fingerprint in LM Studio's server log is unmistakable: repeated token ID 0 (!) rejected as an invalid sample, over and over.

Sampling reduces this failure — it does not remove it

The correct parameters took the Qwen MoE from 0/6 to 3/6 on the synthetic task and 3/4 on the real one. But the token-ID-0 loop still appeared with correct sampling, in one run of four, burning 8,211 reasoning tokens. This is a property of the model that good sampling makes rarer, not a bug that configuration fixes.

Then I ran the same broken configuration against gpt-oss, and it did not care.

Both models under the deliberately broken config (temp 0.3, no truncation), large prompt, 6 runs

gpt-oss was in fact faster with the "broken" settings — 14.4 s median against 16.4 s — because lower temperature made it more decisive and it needed fewer steps.

So the honest version of this finding is narrower than the one I first published: these parameters are not a general fix for local agentic coding. They are a rescue for a model that is fragile to them. If your model needs them, it is telling you something about itself.

Finding 4File size is the wrong number. Compute the KV cache first.

I picked candidate models by weight size, and it led me badly astray. Devstral-Small-2-24B is smaller on disk than the Qwen MoE — 14.39 GB against 15.20 GB — and is far less usable on this machine, because its attention architecture is completely different.

Qwen3.5/3.6 interleave linear-attention layers with full-attention ones; gpt-oss alternates sliding-window and full attention with a 128-token window. Only full-attention layers cost KV cache. Devstral has sliding_window: null — all 40 layers are full attention, at 8 KV heads and head_dim 128.

LM Studio silently capped the context

I requested 16,384 tokens. The model loaded successfully in 6.1 seconds with no warning of any kind — and the CONTEXT column of lms ps read 4,864. Passing --parallel 1 made no difference. The only symptom downstream was an HTTP 400 with "The number of tokens to keep from the initial prompt is greater than the context length" once a realistic prompt arrived. Check lms ps after every load; the number you asked for is not necessarily the number you got.

Devstral itself performed well within that ceiling — 6/6 on the small prompt, 11.4 s median, the fastest of the three, 13 clean tool calls. It is not a bad model on this hardware. It just cannot hold an agent's instructions and a conversation at the same time.

The number to select on is therefore weights + KV cache at the context you actually need, and you can compute it from config.json before spending a single gigabyte of bandwidth. I had this formula in my notes from the second hour and still chose candidates by file size.

And then the runtime decides whether any of it matters

I concluded from the 4,864 ceiling that Devstral was unusable on 24 GB. That was wrong, and the way it was wrong is instructive: I had measured a tool and attributed the result to the model. Three routes to the same weights, three different outcomes:

Driving MLX directly, Devstral handled a 13,728-token prompt in 31.7 s at 16.43 GB peak — proof that neither the model nor MLX has a 4,864-token problem. But mlx_lm.server 0.31.3 cannot surface this model's tool calls: it correctly reports has_tool_calling = True, the model generates 34 tokens, and the response comes back containing nothing but {"role": "assistant"} — no content, no tool_calls. Plain chat works fine; passing tools empties the reply.

The GGUF build is the only route that does both. It costs speed — 132 s per task against 55 s for gpt-oss on MLX — but it is the difference between a usable model and an unusable one.

One more llama.cpp trap: overflow the context and it hangs rather than erroring. I sent a 24,000-token prompt to a 16,384-token context and got silence until LM Studio logged Channel Error fifteen minutes later. MLX returns a clean HTTP 400 for the same mistake. I misread those hangs as "GGUF is unbearably slow" before finding my own overfeeding.

Finding 5The smallest model nearly wins

Qwen3.5-9B is the surprise of the series. At half the weights of gpt-oss it matches its speed, trails its reliability by one run, and needs 39 % of memory instead of 67 %. A 9B of the newer generation beats a 35B of the previous one decisively, at a fifth of the footprint.

Its one failure is benign in shape: run 3 stopped after 4 seconds with a single tool call and 107 reasoning tokens. It ran the tests once and gave up. No loop, no token limit, no degenerate output — a fresh session would have fixed it. That is a different animal from the Qwen MoE's failures, which were expensive and could not be aborted.

Note the context, too: LM Studio granted it 92,672 tokens unprompted, because hybrid attention makes the KV cache cheap. Devstral got 4,864 on the same machine.

Which inverts the question this investigation started with. It began as "which large model still fits" and ends at "which smallest model does the job reliably" — because on this machine, memory headroom converts directly into stability.

Finding 6The engine decides usability, not just speed

Three times in one day, switching from MLX to llama.cpp turned a model from unusable into working. Every time, the failure looked like a model failure in the log.

Qwen3.6-27Bguardrail refuses to load at allloads at full context
Gemma 4 12B0 / 6 — channel-marker loop5 / 6

The Gemma case is the cleanest, because the same model ran the same task through the same harness with the same sampling — the engine was the only variable.

Under LM Studio's MLX path, Gemma's channel markers leak into content as raw text:

<|channel>thought
<channel|>

It starts at 28 characters. After the step that reads duration.py, generation degenerates into nothing but markers — 49,258 characters, 8,191 tokens, length stop — in two independent runs at exactly the same point. reasoning_tokens read 0 throughout.

My first explanation was a feedback loop: the harness writes content back as an assistant message, the model sees its own broken markers and produces more. The control experiment refuted it — with markers stripped (cleaned content: 0 characters at every step) it broke at the same place again. The loop is generated fresh, not fed back.

Under llama.cpp the problem vanishes completely: not a single marker, and reasoning_tokens lands between 225 and 2,797. What is correctly recognised and separated as reasoning there is the garbage that blows up the output under MLX — two sides of the same thing.

The cost is speed

llama.cpp does not use the M5's neural accelerators and runs roughly 2.4× behind MLX. Gemma needs a 156 s median under GGUF against 55 s for gpt-oss under MLX, with heavy variance: four clean runs between 146 and 164 seconds, plus one outlier at 1,226 seconds.

For models that run cleanly under MLX, MLX stays the better choice. But when a model behaves strangely, switching the engine is the first test, not the last.

The moment inference starts the GPU wires them, and wired memory jumps to a plateau in under two seconds. Finding 8You can trade the whole memory problem away — for latency

Everything above fights for headroom inside 24 GB. TurboFieldfare sidesteps the fight entirely: a Swift and Metal runtime, no MLX and no llama.cpp, written for one model — Gemma 4 26B-A4B. It keeps a 1.35 GB shared core resident and streams each token's experts off the SSD. That only works because the model is a mixture of experts with 4B active of 26B total.

The memory claim is not marketing. Measured on the same machine, same day:

A 26-billion-parameter model at 24 % of physical memory. The entire band where the kernel bug in Finding 9 lives — and where this machine's desktop started flickering — simply is not reachable any more. Prompt-prefix reuse works too: 12,642 of 20,087 prompt tokens were served from cache across the series, and the server reports it honestly in usage.prompt_tokens_details.cached_tokens.

And then it is too slow to use

That is the verdict from actually driving it through OpenCode, not from a benchmark: it answers, the analysis is sound, and the wait makes it impractical for interactive work. The project's own README measures 31–35 tok/s on a 24 GB M5 Pro — respectable — but decode speed is not the whole story when every step re-reads experts from storage.

The trade is explicit and it is the right one on the wrong machine. On an 8 GB MacBook Air, where the alternative is "cannot run a 26B model at all", paying latency for feasibility is obviously correct. On 24 GB, where a 12 GB model already fits with headroom to spare, you are paying latency for memory you did not need.

Eleven days old, and it shows

The repair task produced 0/6 here, but that number should not be read as a capability measurement. Two things spoiled it: another model was resident for part of the series (my error — I restored gpt-oss after a reboot and never unloaded it), and every single run hit an HTTP 500 from the server, which I could not reproduce in isolation.

One observation does stand independent of both: across 18 tool calls the model called bash every time and write never once. It ran the tests, saw them fail, and never attempted an edit. Same shape as the Qwen MoE under a long prompt.

The installer is rough in the same way: no timeout on its HTTP range requests, so a dropped connection leaves it waiting silently — mine sat for 53 minutes at 44 % with 0 % CPU and no error. Its --resume is genuinely lossless, which saves the situation, but unattended installation is not something to count on yet.

Worth watching rather than adopting. The first release was 20 July 2026, the OpenAI-compatible server arrived on the 27th, and long-context prefill on the 29th — five releases in ten days.

Finding 9The kernel panic is an unresolved Apple bug, not an MLX one

Mid-session, the machine went down hard:

panic(cpu 12 caller 0xfffffe0050784280):
"pending memory object unexpectedly found in non pending hash"
@IOGPUGroupMemory.cpp:528

Kernel Extensions in backtrace:
  com.apple.iokit.IOGPUFamily(130.13)
  com.apple.AGXG17X(351.2)

Darwin Kernel Version 25.5.0 / OS version 25F80

A known defect class in Apple's IOGPU kernel extension, filed in several places with near-identical signatures:

  • mlx-lm #883 — Qwen3-Coder-30B-A3B in an agentic session, KV cache growing unbounded to ~58k tokens, 80.14 GB wired of 96 GB, panic at IOGPUMemory.cpp:550. The reporter's memory-pressure monitor read false the whole time. Open.
  • mlx #3186 — M4 Max 36 GB, reproducible at ~173k-token prefill. Escalated to Apple as FB22091885. Open.
  • mlx #3346 — M3 Ultra 96 GB, names both bugs as Apple IOGPU kext defects including a race in IOGPUGroupMemory.cpp:219 — same file as my panic, different line. Reporter's conclusion: "the only mitigation is to stop using the GPU entirely."
Why this is worse than it sounds

Wired memory bypasses macOS memory-pressure detection, so nothing warns you before the kernel falls over. A 96 GB machine panicked at 83 % wired. A 15 GB model on a 24 GB machine sits at 80 % during every inference call. The only instrument that sees it is memory_pressure | grep "wired down".

There is one visible warning sign, and it is not in any tool

Late in the session the desktop began to flicker during a Qwen MoE run. Wired was at 20.17 GB — 84 % of physical, the highest reading of the day and past the 83 % at which mlx-lm #883 reports its panic. WindowServer needs GPU memory too, and when it cannot get it, the UI stutters visibly.

That is the only early warning I found in a full day of measuring. Memory pressure still read normal. If your desktop starts flickering while a local model is generating: save your work and unload the model. You are in the band where the kernel bug lives.

macOS 26.6 ships GPU driver fixes — CVE-2026-64691 (unexpected system termination, buffer overflow, improved size validation) and CVE-2026-43723 (memory corruption in a system process). Neither names the IOGPUGroupMemory race. I have not panicked since updating, but a handful of hours proves nothing.

What actually fed it

Not model size, and not a large prefill. The agent log showed step=138 through step=145, four seconds apart and still climbing — an endless loop of 145+ steps, each one growing the KV cache. That loop existed because of the sampling misconfiguration in Finding 2. The kernel bug is real and unfixed; what pushed the machine into it was a bad config.

Do not do what I did

I had raised iogpu.wired_limit_mb to 20480 for more GPU headroom and was about to install a LaunchDaemon to persist it. Don't. mlx-lm #883 recommends moving the wired limit down — from the ~75 % default toward 50–60 % — not up. Raising it lowers the threshold at which the kernel bug becomes reachable. I retracted that and left the sysctl at 0.

Finding 10Three fixes that made things measurably worse

All three seemed obviously right. They are here because I measured them.

The nudging result is the useful one. I assumed the model was choosing prose and could be talked into acting. Nudging does not work — but my conclusion that the state is always terminal was too strong. On the real repair task, one run entered the degenerate loop, kept going, and came out the other side with all 22 tests green after 251 seconds and 12 steps. Another run in the same series went in and never returned. Recovery is possible but not reliable; a fresh session is still the better bet than another turn in a poisoned context.

The max_tokens one is my own misreading. I justified 2048 by pointing at measured reasoning-token counts of 70–210 — but reasoning tokens are a subset of completion tokens, and full completions ran to 2,361. The data was on my screen and I read the wrong column.

Finding 11Tooling behaviour that will cost you an hour each

LM Studio

  • lms get returns exit code 0 when the download fails. Twice — once because it silently lowercased a HuggingFace repo ID. Never trust the return value; check file sizes.
  • Model keys match by prefix. qwen3.6-35b-a3b is a prefix of qwen3.6-35b-a3b-ud-mlx, and with -y it warns "2 models match, loading the first one" and picks whichever. Renaming the directory with a leading dot does not hide it — LM Studio scans dot-directories. Move it out of the models tree and delete ~/.lmstudio/.internal/model-index-cache.json.
  • modelLoadingGuardrails naming is inverted: mode: "high" is the permissive default, mode: "low" is strict. I set it to "low" believing I was relaxing it, and blocked a model that had loaded fine minutes before.
  • The guardrail rejects on weights alone. A 16.08 GB model failed identically at 16,384, 8,192 and 4,096 context with 20 GB free. The "Load Anyway" override exists only in the GUI — the CLI does not expose it even with alwaysAllowLoadAnyway: true.
  • Context can be silently reduced at load time (Finding 4). Always verify with lms ps.
  • Server logs at ~/.lmstudio/server-logs/ are where the real diagnosis lives — reasoning durations, and Zod warnings for degenerate token samples the client never sees.

OpenCode

  • permission defaults to ask for bash and edit. In non-interactive opencode run this hangs forever in the foreground and exits immediately with code 0 and an empty log when stdin is not a TTY. Two contradictory-looking symptoms, one cause. Scope the grant to a project-level opencode.json, not your global config.
  • provider.<p>.models.<id>.temperature is a boolean capability flag, not a value. Putting 0.6 there does nothing. Sampling values go in models.<id>.options or agent.<name>.temperature / top_p.

OpenCode: interactive works, run did not

Every measurement in this document came from a purpose-built harness, because the agent itself kept getting in the way. The final end-to-end check made that concrete: opencode run in non-interactive mode hung in six of seven attempts — 90 to 600 seconds each, killed by watchdog, no output. The process sat at 0.0 % CPU immediately after message=init, before session creation and before any request reached the model server. It was not prompt-dependent: the same one-line prompt completed in 6 seconds once and hung on the next three tries. --pure did not reliably help. I did not find the cause.

The interactive TUI — plain opencode, no subcommand — worked on the first try and built a three-file todo app (HTML, CSS, JS with localStorage persistence) with the same model and config. So if the batch runner stalls on you, that is not your model or your provider config. Use the TUI.

HuggingFace CLI and macOS

  • Never SIGSTOP an hf download. Xet CDN URLs are presigned; suspending the process lets them expire and resume returns 403. Kill and restart.
  • hf download did not resume my .incomplete shards — it discarded 1.5 GB and restarted from zero.
  • Unsloth "UD" (dynamic) quants are much larger than the bit-width implies, keeping some tensors at higher precision. Qwen3.6-35B-A3B-UD-MLX-3bit is 17.4 GB against 15.2 GB for a standard 3-bit — the difference between loading and not loading here. The 27B UD-3bit is 24.05 GB.
  • macOS has no timeout(1). And sudo softwareupdate -i -a --restart downloaded 26.6 to 100 %, exited 0, and never installed it. The GUI updater worked.

Which points at the setup worth considering if you have a second machine: run the large model as a server on the box with the memory, keep the agent on the laptop, and change one line — the provider's baseURL. LAN latency is negligible next to generation time, and the whole memory question disappears.

Saw wired climb 17 → 19 GB in 20 seconds and killed the test. It was the ramp to a flat plateau; two-second sampling later showed 30 MB of drift across a whole generation. I aborted a valid measurement for nothing.

10:28

"The 3-bit quantisation is defective"

I had real evidence: the server rejecting repeated token ID 0, and a log line reading Done reasoning. Reasoned for 807.33 seconds. which I read as one enormous request. Degenerate token emission does indicate a broken quant — it also indicates bad sampling, which is what it was. One malformed tool call in 128.

The 807 seconds were not a request. Hours later the same counter read 36,646 seconds — 10.2 hours, exactly the server's uptime. It is cumulative, not per-request, and I had quoted it as evidence in the first published version of this document.

10:37

"System prompt size is irrelevant"

Built a switchable-prompt harness to prove prompt size was tipping the model over, saw the one-sentence prompt fail identically, and concluded size didn't matter. It didn't — under the broken sampling config. With sampling fixed, prompt size turned out to be the single strongest predictor in the entire study.

10:53

"Cap max_tokens at 2048, successful steps only need 210"

Read my own results table wrong: 70–210 were reasoning tokens; completions reached 2,361.

11:15

"It was the sampling parameters" — published, then refuted

This was the headline of the first version of this document. Then I ran the broken config against gpt-oss for a control and got 6/6, faster than with the "correct" values. The sampling fix is real but scoped to a fragile model. I had generalised from a single subject.

11:41

"Devstral scored 0/6"

Twice wrong. The first 0/6 was HTTP 400 in 0.0 seconds — the prompt exceeded the context ceiling and the model never saw a token. The second was my verification logic: Devstral wrote a correct greet() plus a module-level print, so my checker saw the output twice and called it a failure. Devstral is 6/6.

19:00

"Devstral 2 is not viable on 24 GB"

Published, and wrong. I had measured LM Studio's MLX loader — which caps this model at 4,864 tokens for reasons I never identified — and written it up as a property of the model. Driving MLX directly, the same weights handled 13,728 tokens. Loaded as GGUF, LM Studio gave the full 16,384 requested. The reader who pushed back on this was right and I was not.

19:15

"GGUF is unbearably slow"

Based on three consecutive ten-minute timeouts. They were caused by my own probe sending a 24,000-token prompt into a 16,384-token context — llama.cpp hangs on overflow instead of erroring. Measured properly: 21 tok/s and 132 s per repair task.

20:06

"807 seconds of reasoning on one request"

Quoted as evidence of a broken quant in the first published version. The same counter later read 36,646 seconds — the server's uptime. It is cumulative, and it never meant what I said it meant.

20:10

"The degenerate state is always terminal"

One run on the real task entered the token-ID-0 loop and worked its way out, finishing green after 251 seconds. Recovery is possible — just not reliable.

The pattern

Three of these were my own tooling misread as model behaviour: backgrounding opencode run (EOF on stdin, instant exit 0), the permission prompt (silent hang), and the verification logic (correct code scored as failure). Each looked exactly like the model failing.

With a harness you wrote yourself, the first hypothesis for a surprising result should be the harness — not the model. I reached for the model every time, because that was the interesting answer.

The other three share a different shape: I measured one model, found a real effect, and stated it as a general principle. The control experiment that would have caught all three — run the same broken configuration against a second model — took eleven minutes when I finally did it.

Still openWhat I do not know

  • Whether macOS 26.6 fixes the IOGPUGroupMemory race. The GPU driver CVEs it patches are plausible candidates but do not name it.
  • Why the Qwen MoE degrades specifically under a long system prompt while gpt-oss does not. The what is measured; the mechanism is not.
  • Whether the sliding-window models hold up at genuinely long contexts. Everything here ran at 32k or below, and mlx #3186 reproduces its panic at ~173k prefill.
  • What Devstral-Small-2-24B would do with a real agent prompt on a machine that can hold one. Its 6/6 within a 4,864-token ceiling says nothing about the 32k case.
  • Whether gpt-oss has better sampling values than the Qwen ones I borrowed. Its generation_config.json specifies only do_sample: true.
  • Why opencode run hangs before session creation while the interactive TUI does not. Six failures, no cause found.
  • How this scales past a single file. The repair task is real but small — one module, three bugs, a test suite that runs in a millisecond. Nothing here says anything about a refactor spanning twenty files, or a codebase that does not fit in 32k of context.
  • Whether large tool-call arguments really drive the schema-failure risk. One occurrence in 128 is a hypothesis, not a result.

All numbers measured on one machine on one day: Apple M5 Pro, 24 GB, macOS 26.6 build 25G72, LM Studio 0.4.20 with the MLX runtime. Models: mlx-community/gpt-oss-20b-MXFP4-Q8, mlx-community/mistralai_Devstral-Small-2-24B-Instruct-2512-MLX-MXFP4, NexVeridian/Qwen3.6-35B-A3B-3bit.

The harness was a ~180-line Python loop talking directly to the OpenAI-compatible endpoint, validating tool arguments against the declared schema itself. It exists because the coding agent had to be ruled out as a variable — which, twice, it turned out to be. The repair task used the same loop with the test suite as its success criterion, and verified afterwards that the tests themselves were byte-identical to the originals.

Six runs per configuration. Enough to separate 3/6 from 6/6; not enough to distinguish 5/6 from 6/6. Treat single-run differences as noise. One gpt-oss run took 355 seconds for 375 tokens and is excluded from timing means as a system-level outlier; it is included in the success counts, where it passed.
